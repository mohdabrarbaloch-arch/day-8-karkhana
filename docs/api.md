# API reference

Base URL: `http://localhost:8000`. All endpoints return JSON. Authenticated
endpoints need `Authorization: Bearer <token>`.

## Errors

Validation failures return `422` with FastAPI's standard `detail` array. Business
failures return a plain `detail` string:

```json
{ "detail": "Incorrect email or password" }
```

| Code | Meaning here |
|---|---|
| `400` | The request is well-formed but the action is invalid (e.g. finishing a queued job) |
| `401` | Missing or expired token |
| `403` | Authenticated but wrong role |
| `404` | No such job or node |
| `409` | Conflict — the job is not in a state that allows this |
| `422` | Input validation failed |

## Auth

### `POST /api/auth/register`

```json
{
  "email": "dev@example.com",
  "password": "at-least-eight-chars",
  "team": "research",
  "role": "operator"
}
```

`201` → user object. `409` if the email exists. The first registered user
becomes `admin`; later ones get the role they ask for, capped at `operator`.

### `POST /api/auth/login`

```json
{ "email": "admin@karkhana.dev", "password": "Karkhana2026!" }
```

`200` → `{ "access_token": "...", "token_type": "bearer" }`.
`401` on bad credentials — deliberately the same message for both wrong email
and wrong password, so the endpoint doesn't confirm which emails exist.

### `GET /api/auth/me`

`200` → the current user.

## Nodes

### `GET /api/nodes`

```json
[
  {
    "id": 3,
    "name": "a100-01",
    "cluster_name": "default",
    "gpu_model": "A100-80GB",
    "total_gpus": 8,
    "allocated_gpus": 2,
    "memory_gb": 640,
    "region": "karachi-b",
    "healthy": true,
    "created_at": "2026-11-02T19:28:35.391144Z"
  }
]
```

### `POST /api/nodes` — admin

```json
{
  "name": "hgx-03",
  "gpu_model": "H100-80GB",
  "total_gpus": 8,
  "memory_gb": 640,
  "region": "karachi-a",
  "cluster_name": "default"
}
```

`201` → node. `409` if the name is taken.

There is deliberately **no** per-node price field. Cost is a platform default
(`DEFAULT_COST_PER_GPU_HOUR`, $2.50) with a per-job `rate_override` for the
exceptions, so a node's rate cannot silently drift away from what was quoted.

### `PATCH /api/nodes/{node_id}/health` — admin

```json
{ "healthy": false }
```

`200` → node. This is the only way to change a node's status. Capacity
(`total_gpus`) is set at creation and deliberately not editable here: shrinking
a node out from under running work would make the allocation ledger disagree
with reality.

Marking a node unhealthy does **not** kill its running jobs — that decision
belongs to whoever owns them. It only stops new work landing there.

### `POST /api/nodes/{node_id}/drain` — admin

`200` → message. Marks the node unhealthy, releases every *queued* job pinned
to it back to the pool, and recomputes allocations. Running jobs are left alone
so maintenance can drain rather than amputate.

## Jobs

### `POST /api/jobs`

```json
{
  "name": "urdu-asr-finetune",
  "command": "python train.py --epochs 3",
  "gpus": 4,
  "gpu_model": "H100-80GB",
  "span": "node",
  "priority": 8,
  "duration_minutes": 360,
  "project": "speech"
}
```

- `gpus` — 1 to 64.
- `gpu_model` — `null`/omitted or `"any"` for any model; otherwise an exact
  model string such as `"H100-80GB"`.
- `span` — `"node"` (gang) or `"any"` (spread).
- `priority` — 1 to 10.
- `duration_minutes` — the estimate the backfill reservation is built from.

`201` → `JobDetail`, status `queued`, with a `submitted` entry in `events`.
Captured:

```json
{
  "id": 9,
  "name": "doc-probe",
  "project": "default",
  "command": "echo hi",
  "gpus": 1,
  "gpu_model": "any",
  "span": "any",
  "priority": 5,
  "duration_minutes": 30,
  "status": "queued",
  "node_id": null,
  "submitted_at": "2026-11-02T19:32:56.949792Z",
  "started_at": null,
  "ended_at": null,
  "exit_code": null,
  "last_reason": "",
  "events": [
    { "id": 18, "event": "submitted",
      "message": "Queued for 1 GPU(s), priority 5, estimated 30 min",
      "actor": "admin@karkhana.dev",
      "at": "2026-11-02T19:32:56.951839Z" }
  ]
}
```

Submitting does **not** place the job; that is the scheduler's job, and
separating the two is what lets the API stay fast and the scheduler stay
authoritative.

### `GET /api/jobs?status=queued`

`status` is one of `queued`, `running`, `completed`, `failed`, `cancelled`.
Omit for all.

### `POST /api/jobs/{job_id}/cancel`

`200` → job in `cancelled`. `409` if it already finished or failed — a completed
job is a historical fact and doesn't get rewritten.

### `POST /api/jobs/{job_id}/complete?exit_code=0`

The exit code is a **query parameter**, not a JSON body.

`200` → job in `completed` (exit 0) or `failed` (non-zero). Records `ended_at`
and `runtime_minutes`, which is what the billing formula reads. `409` if the
job isn't running.

## Scheduler

### `GET /api/scheduler/queue`

```json
[
  { "job_id": 5, "reason": "priority 9 → effective 10 after 44 min waiting" },
  { "job_id": 6, "reason": "priority 7 → effective 8 after 54 min waiting" },
  { "job_id": 7, "reason": "priority 3 → effective 3 after 16 min waiting" }
]
```

Ordered the way the scheduler will consider them — effective priority first,
then submission time as the tiebreak. Each entry is a `DeferralRead`: just
`job_id` and the human-readable `reason` explaining its standing.

### `POST /api/scheduler/run`

Runs one pass. No body. Returns a `ScheduleResult`.

Captured from a fresh seed *after* the running jobs were already placed, so
nothing could start — which is itself the interesting case:

```json
{
  "scheduled": [],
  "deferred": [
    { "job_id": 6,
      "reason": "head of queue; needs 24 GPU(s), next capacity window in 176 min" }
  ],
  "unplaceable": [
    { "job_id": 5,
      "reason": "16 GPU(s) of H100-80GB on a single node exceeds every node in the cluster" },
    { "job_id": 7,
      "reason": "2 GPU(s) of L40S-48GB on a single node would fit, but the only matching node(s) are unhealthy (l40s-01)" }
  ],
  "reservation_minutes": 176,
  "head_job_id": 6,
  "message": "Nothing started — no capacity available yet."
}
```

A `scheduled` entry carries `job_id`, `node`, `gpus` and `reason`:

```json
{ "job_id": 8, "node": "a100-01", "gpus": 2,
  "reason": "started Job #8 -> a100-01 (2 GPU, backfill)" }
```

Every queued job appears in exactly one of `scheduled` / `deferred` /
`unplaceable` — 3 queued jobs and 3 array entries above. The distinction is
deliberate: **deferred** means *waiting for capacity that will exist*, and it is
the only category that may hold the reservation; **unplaceable** means *no
amount of waiting helps until hardware or the request changes*, and reporting
those as "waiting" would be a lie the operator can't act on.

### `POST /api/scheduler/reset`

`200` → message. Returns every `running` job to `queued` and zeroes allocations.
A demo convenience, and a real recovery tool if the counter ever disagrees with
the jobs that justify it.

## Dashboard

### `GET /api/dashboard`

Captured from a fresh `ALLOW_DEMO_SEED=true` database:

```json
{
  "total_gpus": 28,
  "allocated_gpus": 4,
  "free_gpus": 24,
  "utilisation_percent": 14.3,
  "nodes": 4,
  "healthy_nodes": 3,
  "jobs_queued": 4,
  "jobs_running": 1,
  "jobs_completed": 2,
  "jobs_failed": 1,
  "gpu_hours_today": 0.0,
  "cost_today": 0.0,
  "per_node": [
    { "name": "a100-01", "gpu_model": "A100-80GB", "total_gpus": 8,
      "allocated_gpus": 0, "free_gpus": 8, "utilisation_percent": 0.0,
      "healthy": true, "region": "karachi-b" }
  ]
}
```

`utilisation_percent` is `allocated_gpus / total_gpus × 100`. Because a dead
node still counts toward `total_gpus`, taking `l40s-01` down lowers utilisation
rather than hiding its capacity.

Note `gpu_hours_today` and `cost_today` are **0.0** on a fresh seed: the seeded
historical jobs ended days ago, and "today" starts at UTC midnight.

### `GET /api/dashboard/chargeback?days=30`

```json
{
  "period_start": "2026-10-03T19:28:39.174916Z",
  "period_end": "2026-11-02T19:28:39.174916Z",
  "total_gpu_hours": 9.88,
  "total_cost": 24.71,
  "teams": [
    { "team": "research", "jobs": 2, "gpu_hours": 6.95, "cost": 17.38,
      "job_ids": [2, 3] },
    { "team": "platform", "jobs": 1, "gpu_hours": 2.9333, "cost": 7.33,
      "job_ids": [4] }
  ]
}
```

**Billed statuses are `completed`, `failed` and `cancelled`.** Running work is
excluded because its billed minutes aren't known yet — billing a job twice as
it runs is how chargeback loses trust. Cancelled work *is* charged: it held
GPUs for the time it ran.

The arithmetic is meant to be checkable by hand. Both rows use the $2.50/GPU-h
default, and each is `gpu_hours × 2.50` rounded to cents: `6.95 × 2.50 = 17.375
→ 17.38`, `2.9333 × 2.50 = 7.333 → 7.33`. The totals are the sums of the rows:
`17.38 + 7.33 = 24.71`.

### `GET /api/dashboard/teams`

Distinct team names, for populating a filter. Admins see all; an operator sees
their own.
